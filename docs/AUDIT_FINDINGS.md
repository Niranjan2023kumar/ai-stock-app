# Audit Findings (2026-07-17) - 11 dimensions + critic, all verified adversarially

## DIMENSION: angelone-api
SUMMARY: The SmartAPI integration is protocol-accurate and largely real: the login call, TOTP generator, WebSocket subscribe frame, and binary LTP parsing all match the Angel One spec byte-for-byte (I verified the endpoint responds live with SmartAPI JSON), and the app degrades gracefully to Yahoo when no keys exist. However, it is significantly under-wired: real-time ticks reach only two display spots on the Stock/Home tab, while the Intraday tab and — critically — the stop-loss/target TradeWatchService still run entirely on ~90-second Yahoo polling, so the feature a trader most needs real-time data for gets none of it. Resilience (permanent give-up after 3 login failures with no user-visible error) and credential storage (MPIN/TOTP secret in plaintext DataStore) are the other material gaps.

### [high] Real-time feed is not wired into the stop-loss watcher or the Intraday tab — the paths that need it most
FILE: app/src/main/java/com/example/myapplication3/tracking/TradeWatchService.kt
DETAIL: The SmartAPI live tick stream (SmartApiFeed.livePrices) is consumed in exactly two display spots, both on the Stock/Home tab: the hero decision card (HomeScreen.kt line 730) and the "Your stocks" cards (lines 752-754). TradeWatchService.watchLoop() — the foreground service that fires stop-loss and target alerts — fetches prices via marketRepo.fetchPricesForSymbols(symbols), which is a Yahoo v7 batch call (IntradayRepository.kt lines 228-236), on a 90-second loop (CHECK_INTERVAL_MS = 90_000L). TradingScreen.kt (the Intraday tab) contains zero references to livePrices or liveConnected, so the master signal card, stale-entry protection (C12a), and position calculator all run on delayed Yahoo snapshots even when the user has configured Angel One. The SmartApiFeed doc comment claims "This is the true real-time source; the rest of the app falls back to Yahoo when it isn't connected" — that is only true for two cards.
IMPACT: A user who spends 10+ minutes setting up SmartAPI keys expecting real-time protection still gets stop-loss alerts up to ~90 seconds late (plus Yahoo's own delay), and the Intraday tab — the tab where seconds matter — shows the same delayed prices as before. In a fast fall, that delay is real money lost after the stop was breached.
FIX: Inject SmartApiFeed into TradeWatchService and prefer feed.livePrices[symbol] (when feed.connected) over the Yahoo fetch in watchLoop; collect livePrices/liveConnected in TradingScreen (the shared activity-scoped InterdayViewModel already exposes them) and use the effective-price pattern already used by OneDecisionCard for the master card and stale-entry check.

### [medium] Feed permanently gives up after 3 login failures with no recovery and no user-visible error
FILE: app/src/main/java/com/example/myapplication3/smartapi/SmartApiFeed.kt
DETAIL: runFeed() breaks out of the control loop after MAX_LOGIN_FAILURES=3 consecutive login failures ("giving up live feed until keys change", lines 110-118). But the only restart trigger is InterdayViewModel's smartApiStore.isConfigured.distinctUntilChanged() collector (InterdayViewModel.kt lines 215-222) — a Boolean that stays true, so re-saving the same valid keys never re-emits and nothing ever calls start() again until the process dies. Three transient failures (phone offline at app launch, Angel maintenance window at 8:59 AM, DNS blip) kill live data for the entire session. Nothing is surfaced to the UI: connected just stays false, so the "● Live" tag silently never appears.
IMPACT: A user whose phone had spotty network at app open trades all day on delayed Yahoo data believing live data is on (they tested keys yesterday and saw "Connected"). There is no error card, no retry button, no hint — the only symptom is the absence of a small green tag.
FIX: Distinguish credential errors (invalid TOTP/MPIN/key → stop and surface a message) from transient errors (network/5xx → keep retrying with capped backoff, or retry on connectivity-restored callback). Expose a feedState: StateFlow<FeedState> (Connected/Connecting/GaveUp(reason)) and show a one-line "Live data paused — tap to retry" card when GaveUp; also restart on isConfigured re-save by keying on the credentials object rather than the Boolean.

### [medium] Trading-capable credentials (MPIN, TOTP secret, API key) stored in plaintext preferences
FILE: app/src/main/java/com/example/myapplication3/smartapi/SmartApiStore.kt
DETAIL: SmartApiStore writes apiKey, clientCode, mpin, and totpSecret into the plain Preferences DataStore ("stock_intelligence_prefs", provided in di/AppModule.kt lines 14-15 with no encryption). The settings card itself warns "⚠️ These keys can also place trades" (SmartApiSettingsCard.kt line 120), and the TOTP secret is a permanent second factor — together with MPIN and API key, this file contains everything needed to log in and trade as the user. android:allowBackup="false" mitigates backup extraction, but the file is readable on any rooted device, by malware with root, or from a discarded/stolen unlocked phone image. Requirements E6 explicitly asks for encrypted-capable local storage.
IMPACT: If the phone is rooted, compromised, or imaged, an attacker gets the user's full Angel One trading access (MPIN + TOTP secret + API key = complete login), not just price data. For a retail trader this is their brokerage account.
FIX: Wrap the four values with Android Keystore encryption: either androidx.security EncryptedSharedPreferences, or encrypt each value with a Keystore AES key before writing to DataStore. Migration is simple since the store is a single class with save()/current().

### [medium] Instrument master downloads the full multi-MB scrip file into one String and never refreshes its cache
FILE: app/src/main/java/com/example/myapplication3/smartapi/InstrumentMaster.kt
DETAIL: ensureLoaded() fetches https://margincalculator.angelbroking.com/OpenAPI_File/files/OpenAPIScripMaster.json — a file with 100k+ instruments, tens of MB — via it.body?.string() (entire body as one String) and then org.json JSONArray(body) (a second full in-memory representation) on lines 68-71. On budget Android phones with 192-256MB heap this is an OOM/ANR risk, and it burns significant mobile data (violating the app's own data-saver rule E3d). Separately, the disk cache ("nse_eq" in SharedPreferences) has no TTL and is never invalidated (lines 57-65), so token changes, new listings, and symbol changes after the first successful download are never picked up — a symbol whose token changes silently stops ticking forever, with only a log line ("no tokens resolved") if the whole map is empty.
IMPACT: First-time setup on a low-RAM phone can crash or freeze the app during the invisible master download; on mobile data it silently eats a large chunk of the user's daily quota. Months later, a stock whose token changed shows no live price with no explanation — the card quietly falls back to delayed Yahoo data.
FIX: Stream-parse the response with android.util.JsonReader directly from the response body stream (filtering NSE -EQ rows as they stream, never holding the full file), and add a cache timestamp with a weekly (or on-failure) refresh. Optionally do the first download only on Wi-Fi or show a one-time size notice.

### [low] Symbol subscription set only updates after a socket drop; no resubscribe while connected
FILE: app/src/main/java/com/example/myapplication3/smartapi/SmartApiFeed.kt
DETAIL: start() sets desiredSymbols and returns if the control loop is already active (lines 86-91); the token list is resolved once per connection in runFeed() (line 122) and the subscribe frame is sent only in onOpen. The doc comment admits it: "it just adopts the new symbol set on the next (re)connect." There is no action:1 subscribe message sent for newly desired tokens on a live socket, and no unsubscribe (action:0) support at all.
IMPACT: Today the watchlist is static so this is latent, but the moment anything calls start() with a different set (e.g. a user-added watchlist symbol, or the search screen wanting a live quote), the new symbol gets no live ticks until the socket happens to drop — which with a healthy connection can be hours.
FIX: In start(), if the socket is currently open and the symbol set changed, resolve tokens for the delta and send an additional subscribe frame (and optionally action:0 unsubscribe for removed tokens) instead of waiting for a reconnect.

### [low] Feed runs 24/7 once started — no market-hours gating and no lifecycle stop
FILE: app/src/main/java/com/example/myapplication3/smartapi/SmartApiFeed.kt
DETAIL: SmartApiFeed is a @Singleton with its own SupervisorJob scope; once InterdayViewModel's init starts it, stop() is only ever called if the user deletes their credentials (InterdayViewModel.kt line 220). There is no market-hours check anywhere in the feed (contrast TradeWatchService.isMarketHours()), so the WebSocket stays connected — and reconnects with backoff on every drop — all night, all weekend, and while the app is backgrounded, keeping the 25s ping loop and OkHttp socket alive.
IMPACT: Small but permanent battery and data drain overnight for zero benefit (NSE sends no ticks when closed), on a user base the requirements describe as data-conscious budget-phone owners (rule E3d).
FIX: Gate the connect attempt in runFeed() on NSE market hours (reuse TradeWatchService.isMarketHours()) with a long sleep until next open, and/or stop the feed when the app process goes to background via ProcessLifecycleOwner.

### [low] Server text frames (subscription errors) are silently ignored
FILE: app/src/main/java/com/example/myapplication3/smartapi/SmartApiFeed.kt
DETAIL: The WebSocketListener only overrides onMessage(webSocket, bytes: ByteString) for binary frames (line 187). SmartAPI WS 2.0 sends error responses to bad subscription requests as text/JSON frames (errorCode/errorMessage), and "pong" heartbeat replies as text; onMessage(webSocket, text: String) is never overridden, so a rejected subscription (bad token, quota exceeded, invalid feed token variant) produces no log and no state change — connected stays true while zero ticks arrive.
IMPACT: The user sees "● Live (Angel One, real-time)" at the top of the screen while every price on screen is actually the Yahoo fallback — the exact honesty failure rule B6 forbids.
FIX: Override onMessage(text) and log/parse JSON error frames; if a subscription error arrives, either resubscribe or set connected=false so the UI stops claiming live data. Consider setting connected=true only after the first binary tick rather than in onOpen.

### [low] Concurrent logins possible: ensureSession()/login() have no mutual exclusion
FILE: app/src/main/java/com/example/myapplication3/smartapi/SmartApiClient.kt
DETAIL: session is a @Volatile var and login() has no Mutex; the feed's reconnect path (ensureSession(), line 109) and the settings card's Test button (SmartApiViewModel.test() calling client.login()) can run simultaneously, producing two loginByPassword calls in the same second. Angel One rate-limits loginByPassword (1 req/sec) and repeated logins can invalidate the earlier session's tokens depending on server policy.
IMPACT: Pressing "Test connection" while the feed is reconnecting can cause a spurious "exceeding access rate" failure or briefly kill the live socket's session — confusing one-off errors the user cannot explain.
FIX: Guard login() with a kotlinx.coroutines.sync.Mutex (or share a single in-flight Deferred<Result<SmartApiSession>>) so concurrent callers await one login.

### [low] Non-JSON login failures surface cryptic parser text to the user
FILE: app/src/main/java/com/example/myapplication3/smartapi/SmartApiClient.kt
DETAIL: login() never checks resp.code and immediately does JSONObject(text) on the body (lines 80-81). If Angel's WAF/CDN returns an HTML error page, an empty body, or a 403, the user-visible Test result becomes "✗ Value <html of type java.lang.String cannot be converted to JSONObject" or "✗ End of input at character 0". Also note the error-key casing: my live probe of the endpoint returned {"success":false,...,"errorCode":"AG8001"} — the fallback on line 83 reads optString("errorcode") (lowercase), which misses that variant; it currently works only because "message" is populated.
IMPACT: A beginner (the app's explicit target user) seeing a Java parser exception in the settings card has no idea whether their keys are wrong, their internet is down, or the app is broken.
FIX: Check resp.isSuccessful / resp.code first and map to plain messages ("Angel One server not reachable right now — try again"), wrap the JSON parse in a friendly fallback, and read both "errorcode" and "errorCode".

### [low] No device clock-skew guidance for TOTP failures
FILE: app/src/main/java/com/example/myapplication3/smartapi/Totp.kt
DETAIL: Totp.generate() uses System.currentTimeMillis() with the standard 30s step and no drift handling. That is correct RFC 6238, but on Indian budget phones with automatic time disabled, a clock off by ±1 minute makes every login fail with Angel's "Invalid totp" message. The app relays that message verbatim (SmartApiClient login error path) with no hint that the phone's clock — not the pasted secret — is the cause, and the feed's 3-failure give-up (SmartApiFeed) then disables live data entirely.
IMPACT: A user with a slightly wrong clock concludes their carefully-copied TOTP secret is bad, re-does the whole enable-totp flow, fails again, and gives up on live data — when the fix was Settings > Date & time > automatic.
FIX: When the login error message contains "totp" (case-insensitive), append a hint: "Also check that your phone's Date & Time is set to automatic — a wrong clock breaks TOTP." Optionally compare device time against the Date header of the login HTTP response and warn on >30s skew.

## DIMENSION: data-realness
SUMMARY: The app's live surfaces (Stock/Home, Intraday/Trading, Scanner, Mutual Funds, Research, More Ways) are genuinely fed by real network data — Yahoo Finance v7/v8 quotes and 1-year candles, mfapi.in (AMFI) NAVs, NSE India endpoints with an honest Yahoo fallback, optional Angel One SmartAPI websocket ticks — and the project contains NO random-number-generated or invented market data (the only Random/shuffled use is a legitimate Monte Carlo resampler in the dormant backtesting module). Core formulas (Wilder RSI, EMA/SMA/MACD/ATR/Bollinger/VWAP, CAGR, annuity-due SIP projection, P&L arithmetic, prev-close %-change handling) are correct, and there is extensive honest labeling of cached/stale/missing data. The significant problems are: the background WorkManager protection path monitors a database table that is never populated (so its stop-loss/target/daily-loss alerts can never fire), score-derived numbers presented as probabilities/"chance", a pseudo-"ATR" whose floor fabricates volatility when Yahoo omits the day range, 52-week bounds silently labeled as N-day extremes on two screens, a position calculator that tells users they can buy shares they cannot afford, and realized P&L that ignores brokerage charges the requirements explicitly demand be deducted.

### [high] Background stop-loss/target/daily-loss alerts monitor a table that is never written — protection silently dead
FILE: notifications/src/main/java/com/example/myapplication3/notifications/worker/ScannerWorker.kt
DETAIL: ScannerWorker (enqueued as 5-min periodic work in MainActivity.kt:64-67) calls portfolioRepository.getOpenPositionsOnce() for exit alerts and portfolioRepository.calculateDailySummary() for daily-loss warnings. But PortfolioRepository.openPosition() has zero callers anywhere in the codebase (grep confirms only its definition) — real trades are recorded in the separate TradeTrackerRepository/TrackedTradeDao. openPositions is therefore always empty and checkExitAlerts()/checkDailyLossLimit() always no-op. TradeWatchService.kt:107 even claims "the 15-min WorkManager scan backs us up" — that backup does not exist. InterdayViewModel.kt:296-298 acknowledges the same dead table for in-app limits but the worker was never migrated.
IMPACT: The requirements promise alert-only protection that survives the foreground service being killed (locked decision #2, E1). In reality, once Android or an OEM battery killer stops TradeWatchService (guaranteed after ~6h on Android 14+ via onTimeout), no stop-loss alert will ever arrive from the background path. A user holding a falling position, trusting "the app will alert you", receives nothing.
FIX: Point ScannerWorker at TradeTrackerRepository.getAllOpenOnce() (real, non-practice trades) for SL/target checks, and compute the loss-limit check from tradeTracker.observeTodayRealized + the daily capital limit, mirroring InterdayViewModel's logic.

### [medium] Invented up/down/sideways percentages shown to the user as "Estimated chance"
FILE: app/src/main/java/com/example/myapplication3/ui/screen/TradingScreen.kt
DETAIL: SignalEngine.kt:177-182 fabricates upsideProbability = 35 + points/max*40 (clamped 40-80), downProb = max(10, 70-upside), sideways = remainder — a linear re-mapping of the internal score, not a measured or calibrated probability. TradingScreen's MasterSignalCard labels it honestly ("Signal lean (rough guide, not a real chance)", line 1811), but RewardVsRiskCard at lines 610-620 shows the same numbers under the label "Estimated chance" with "⬆ 65% ➡ 20% ⬇ 15%" — presenting an invented statistic as odds.

### [medium] "ATR-based" stop/target levels are not ATR, and fall back to a fabricated 1.5% range when Yahoo omits day high/low
FILE: app/src/main/java/com/example/myapplication3/intraday/SignalEngine.kt
DETAIL: Lines 153-155: `val dayRange = if (q.dayHigh > q.dayLow) q.dayHigh - q.dayLow else q.price * 0.015; val atr = maxOf(dayRange * 1.5, q.price * 0.012)`. This is a single-day range heuristic, not the 14-day ATR the requirements specify (H5: "stop-loss = 1×ATR"); a real ATR implementation exists unused for this path in scanner/technical/TechnicalIndicators.kt:70. Worse, when Yahoo returns no day range (dayHigh==dayLow, common at open or for v8-parsed quotes where meta omits it), dayRange becomes an invented price*1.5%, so every displayed level — stop-loss, T1, T2, T3, trailing stop, expected profit/loss, and the recommended quantity derived from the loss — is manufactured from a constant, then shown as precise rupee prices. The comment at line 289 ("no fabricated range — dayHigh==dayLow triggers the engine's honest fallback") mislabels this fallback as honest. H5's "target respects nearby swing-high resistance" is also entirely absent.
IMPACT: The user places real Groww orders at stop/target prices presented as engine-calculated levels; on days when the data behind them is a hardcoded 1.2-2.25% of price, the "protection" distance has no relationship to the stock's actual volatility — stops far too tight for volatile smallcaps, too wide for quiet largecaps.
FIX: Compute a true 14-period ATR from the historicalCloses+day ranges already fetched by the v8 path (1y of daily data is available for the top-90 symbols); when no history exists, either skip the signal or visibly mark levels as rough estimates rather than exact prices.

### [medium] 52-week bounds displayed as "20D Low/High" for the ~110 symbols without close history
FILE: app/src/main/java/com/example/myapplication3/intraday/IntradayRepository.kt
DETAIL: computeScreenerItems (lines 249-259) substitutes 52-week high/low for the selected N-day period when a quote has no historicalCloses — which is true for every symbol beyond the top-90 priority list, since only v8 chart fetches carry history (line 139-140) and "v7 quotes carry no close history" (line 249 comment admits the substitution). HomeScreen.kt:1426-1427 honestly relabels these rows as "1 year", but TradingScreen.kt:1095/1102 and ScannerScreen.kt:478/488 print the chips unconditionally as "${days}D Low ₹X" / "${days}D High ₹X". distFromPeriodLowPct/HighPct used for filtering/ranking are computed from the same wrong bounds.
IMPACT: A user filtering for "stocks at their 20-day low" sees mid/small-cap rows whose "20D Low" is actually the 52-week low — a materially different (much stronger) claim about how cheap the stock is, driving buy decisions on mislabeled data.
FIX: Propagate the hasRealPeriod flag (historicalCloses.isNotEmpty()) into StockScreenerItem and relabel the chips "52W Low/High" in TradingScreen's PeriodStatChip and ScannerScreen's ScanChip when the fallback was used, matching HomeScreen's honest handling.

### [medium] Position size calculator claims the user "can buy 1 share" they cannot afford, and ignores the risk-cap sizing rule
FILE: app/src/main/java/com/example/myapplication3/ui/viewmodel/InterdayViewModel.kt
DETAIL: setCapitalInput (lines 564-570): `val qty = maxOf(1, (amount / topSignal.currentPrice).toInt())`. With ₹500 capital and a ₹2,900 stock, (amount/price).toInt() = 0 but maxOf(1, 0) forces qty=1, and TradingScreen.kt:674-676 then renders "With ₹500 you can buy 1 share of RELIANCE @ ₹2,900" — factually false. ### [medium] Realized P&L, loss limits and practice mode ignore trading charges required by the spec
FILE: app/src/main/java/com/example/myapplication3/tracking/TradeTrackerRepository.kt
DETAIL: close() (line 78-82) computes `pnl = (exitPrice - entryPrice) * quantity` with no brokerage/STT deduction. This gross figure drives the always-visible "Today: +₹X" bar (TodayPnlBar), the daily/weekly loss limits (InterdayViewModel.dailyLossBreached), and the weekly report card. Requirement H11 explicitly demands practice-mode profit be shown AFTER realistic charges and slippage, and B0.3a's whole premise is that ~₹50-60 round-trip charges eat small-capital profit. HomeScreen's hero pick honestly deducts FLAT_CHARGES_RS (line 1237) for the projection, but the realized numbers the user actually banks on do not. TradingScreen's RewardVsRiskCard (+₹X/share, lines 593-601) and Max Gain totals also show gross figures with no charges note.
IMPACT: "Today: +₹40" can be a real-money net loss after ₹50-60 charges. Small-capital users — the group the app most protects — systematically overestimate earnings, and practice mode builds exactly the false confidence H11 was written to prevent.
FIX: Subtract the same flat round-trip charge constant (already defined in HomeScreen, move it to core Constants) inside TradeTrackerRepository.close(), or store gross and net and display net everywhere the ₹ P&L is shown; label practice results per H11.

### [low] Rupee change figure on Stock Research uses the wrong base price

### [low] "5% of today's money" daily loss limit floors at ₹1,000 — which is up to 50%+ of a small user's capital
FILE: app/src/main/java/com/example/myapplication3/ui/viewmodel/InterdayViewModel.kt
